# Change log

## 2026-10-25T04:56:29+05:30 — Real neighbourhoods (Phase 1, item 3)

- Changed: `/api/me` now assigns the neighbourhood on the server from the person's home cell with the existing engine (`src/lib/hood/server.ts` → `assignNeighbourhood`), saves it to `neighbourhoods`, keeps `member_count` current and returns it, and the phone takes the server's neighbourhood over its own placeholder (`useCloudSave.ts`). New `/api/hoods/rebalance` regroups everyone nightly (Vercel cron in `vercel.json`, 02:30 IST, `CRON_SECRET` bearer) or on demand with `POST`; `planRebalance` is the pure core. New migration `supabase/migrations/0003_neighbourhoods.sql` adds `my_neighbourhood_stats(day)` and `my_neighbourhood_board(day)`: masks and today's points for the caller's own neighbourhood only. Play, Map and Ask show real member counts, played-today and the leaderboard from those functions once a neighbourhood has 5 players (`src/lib/app/live.ts`, `useLiveHood.ts`, `GameHub.tsx`, `HoodView.tsx`, `AskView.tsx`); below that the labelled sample content stays, with the real count so far. The "sample" tags disappear only when the data is real.
- Why: Phase 1 item 3. Neighbourhoods are sized by people, not kilometres, and that can only be done where all the people are: on the server.
- Validation: `npm test` passed (84 tests in 9 files; new `src/lib/hood/server.test.ts` for the rebalance plan and `src/lib/app/live.test.ts` for the real-or-sample rules), `npm run typecheck` and `npm run build` passed (`/api/hoods/rebalance` in the route list). Smoke test with `next start` and no keys: the rebalance route answers 503 without `CRON_SECRET`, 401 with a wrong token and 503 (database not connected) with the right one. Not run against a live Supabase project.
- Limitations: with few players the rebalance pools everyone into one resolution-6 hexagon (about 36 sq km) until there are 30 or more, so early neighbourhoods are large; a person's neighbourhood can change overnight, and their open questions stay with the old one until Ask is real (item 4). Empty neighbourhoods are kept with a count of 0. The Vercel Hobby plan runs crons once a day at most.

## 2026-10-25T04:46:53+05:30 — Accounts and saved progress (Phase 1, items 1, 2 and 7)

- Changed: masked play now signs in anonymously through Supabase when the project allows it, and "Continue with Google" links that account (or signs in afresh and copies this phone's progress) (`src/lib/app/useGoogleAccount.ts`, `state.ts`). A signed-in person's mask, hero name, home hexagon, neighbourhood, trust level, Thanks, streaks and each day's results are saved to their account through a new `/api/me` route (`src/app/api/me/route.ts`, `src/lib/app/sync.ts`, `useCloudSave.ts`); an existing browser state is copied into the account on first sign-in. New migration `supabase/migrations/0002_accounts.sql` (never edits 0001): `users.auth_user_id`, `provider`, `mask_style`, `best_streak`, a `daily_plays` table, own-row RLS policies and a `my_neighbourhood_members()` function that returns mask fields only. Me explains where progress is saved; Onboarding's mask card says whether progress is saved (`MeView.tsx`, `Onboarding.tsx`, `KavalaApp.tsx`).
- Privacy: new `src/lib/privacy/coordinates.ts` finds coordinate keys at any depth; `/api/me` and the beacon refuse such bodies with 422 (the beacon used to check top-level keys only). Spot guesses (map taps) and the place's position never leave the phone; only points and the best distance are saved. The trust level saved on the server comes from the sign-in (Google = verified, anonymous = masked), not from the phone.
- Why: Phase 1 items 1 (accounts), 2 (saved progress) and 7 (privacy proof) of the plan; progress should survive a cleared browser and a new phone without anyone handing over their name.
- Validation: `npm test` passed (79 tests in 7 files: new `sync.test.ts` for the snapshot, merge and validation rules and `privacy.test.ts` proving nested coordinates are refused by the beacon and `/api/me`, that a valid body without a database gets 503 not a fake success, and that no migration gives any table but `places` a coordinate column); `npm run typecheck` and `npm run build` passed. Not run against a live Supabase project: this environment has no Supabase keys, so the anonymous sign-in, Google linking and `/api/me` writes still need checking on the Vercel deployment.
- Limitations: a daily played on one phone shows as not played on a second (results, not the map, are saved; the streak is safe). Thanks are still only earned from sample neighbours until Ask is real (item 4), so the saved count is what the phone reports. Neighbourhood assignment is still done on the phone (item 3 moves it to the server). "Verify phone (demo)" stays local and is still a demo.
